Wox 2.0 和 Flow Launcher 的 Node.js 插件确实存在架构差异，但不需要编写两个 C++
插件。我们可以在现有的 node-host.js 这一层通过逻辑判断来完美兼容两者。

1. 兼容性分析

┌────────┬───────────────────────────────────────────┬─────────────────────────────┐
│ 特性   │ Wox 2.0 (CustomCommands 为代表)           │ Flow Launcher (HelloWorld   │
│        │                                           │ 为代表)                     │
├────────┼───────────────────────────────────────────┼─────────────────────────────┤
│ 调用方 │ Module 模式：宿主进程加载 JS              │ CLI                         │
│ 式     │ 文件并持续运行，通过调用导出函数（query） │ 模式：每次查询启动一个新的  │
│        │ 通信。                                    │ Node.js                     │
│        │                                           │ 进程，通过命令行参数传递请  │
│        │                                           │ 求，从 stdout 获取 JSON。   │
│ 性能   │ 高：进程常驻，有内存状态，响应快。        │ 中：每次启动进程有开销（约  │
│        │                                           │ 100-200ms），但更稳定且解耦 │
│        │                                           │ 。                          │

结论：在我们的 node-host.js 中已经实现了初步的类型检测（isModule）。我们只需要继续完善
node-host.js 的“翻译”层，让它能够根据插件类型选择不同的调用协议。

2. CustomCommands 激发方式

CustomCommands 插件的 plugin.json 中配置了 "TriggerKeywords":
["*"]，这意味着它应该拦截所有输入。

目前无法激发的原因：
1. Mock API 限制：它的 index.js 在 init 时会通过 api.GetSetting(ctx, "shortcuts")
   获取配置。目前我们在 node-host.js 中提供的 Mock API 总是返回
   []，所以它认为没有命令可以显示。
2. 触发逻辑：虽然关键词是 *，但它在 query 逻辑中会判断输入是否匹配已定义的 shortcut
   名字。
